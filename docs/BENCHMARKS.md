# Phase 0 实测结果

机器：Apple M4 Pro / 24 GB · mlx 0.32.4 · mlx-audio 0.6.5 · mlx-lm 0.32.2 · 2026-11-12

复现：
```bash
.venv/bin/python bench/asr_bench.py mlx-community/Qwen3-ASR-0.6B-8bit 300
.venv/bin/python bench/transcribe_dictation.py
FEWSHOT=bench/fewshot.json .venv/bin/python bench/llm_bench.py mlx-community/Qwen3.5-4B-MLX-4bit
```
原始数据在 `bench/results_asr.jsonl`、`bench/results_llm.jsonl`。

## 1. 语音识别（FLEURS cmn_hans_cn test，前 300 条，平均 11.6 s/条，真人朗读）

| 模型 | CER 全部 | CER 不含数字/英文 | 整条延迟（均值 / p90） | 实时倍数 | 尾段延迟 1s / 2s / 3s / 5s | 峰值内存 |
|---|---|---|---|---|---|---|
| **Qwen3-ASR-0.6B-8bit** | 7.71% | **2.23%** | 0.20 / 0.28 s | 58× | **60 / 69 / 78 / 110 ms** | 2.2 GB |
| Qwen3-ASR-1.7B-8bit | 7.06% | 1.93% | 0.40 / 0.57 s | 29× | 92 / 114 / 141 / 215 ms | 3.8 GB |
| 0.6B-8bit，自动语种检测 | 7.75% | 2.23% | 0.21 / 0.29 s | 55× | 64 / 78 / 88 / 119 ms | 2.2 GB |

- "CER 全部"偏高，主要原因是数字写法不同（参考答案写"15 米""2011 年"，模型输出"十五米""二零一一年"），并不是识别错误。"不含数字/英文"子集（6857 字）才反映真实的识别准确率。**数字转换（ITN）交给润色层处理。**
- 8-bit 模型开启自动语种检测，没有出现空输出，也没有精度损失（之前报告的空输出问题只出现在 4-bit）。
- `felixfu824/...-mixed-6-8bit` 在 mlx-audio 0.6.5 上加载失败（`conv_out` 形状不匹配），已放弃。8-bit 已经够用。
- `hotwords=[...]` 有效：传入"UI稿"后，"UI 搞"被纠正为"UI 稿"。但"database"（TTS 发音含糊，被识别成"day to day"）没有被纠正。
- **结论：默认用 0.6B-8bit。** 松开热键后，剩下 2–3 秒音频的识别只要约 70–80 ms。1.7B 准确率只好 0.3 个百分点，延迟却翻倍，作为可选项。

## 2. 润色 LLM（8 条 TTS 口述样本，输入为 0.6B 的真实 ASR 输出）

样本包含：口头禅、改口、列举、中英混说、翻译指令、短句。ASR 本身也引入了错误（"嗯"→"问"、"呃"→"恶"、"UI 稿"→"UI 搞"、"database"→"day to day"）。

### 延迟（8 条平均，few-shot 版 prompt，系统前缀 500–530 tokens）

| 模型 | 冷启动 TTFT | **缓存前缀后 TTFT** | 解码速度 | 生成完毕 | PLD 加速 | 峰值内存 |
|---|---|---|---|---|---|---|
| Qwen3-4B-Instruct-2507-4bit | 0.66 s | 64 ms | 82 tok/s | 0.32 s | 1.37×（输出逐 token 一致） | 2.9 GB |
| Qwen3-1.7B-4bit | 0.27 s | 46 ms | 166 tok/s | 0.17 s | 1.53× | 1.5 GB |
| **Qwen3.5-4B-MLX-4bit** | 0.63 s | **73 ms** | 76 tok/s | **0.35 s** | 不可用 | 3.1 GB |
| Qwen3.5-2B-MLX-4bit | 0.24 s | 30 ms | 147 tok/s | 0.17 s | 不可用 | 1.6 GB |

- **前缀缓存是最大的收益**：TTFT 降到原来的 1/4～1/10。few-shot 示例从 196 加到 530 tokens 后，缓存后的 TTFT 不变（64 ms 和 71 ms 基本一样）。示例写多少都不影响运行时延迟，只在启动时多花约 0.6 s。
- **Prompt-lookup 投机解码**（`bench/llm_bench.py` 里的 `pld()`，约 40 行）：在纯注意力模型上平均加速 1.3–1.7×，单条最高 2.2×，输出和贪心解码逐 token 一致。翻译、大幅改写时没有收益，有一条（d06）还变慢了（0.84×），需要按命中率自适应关闭。
- **Qwen3.5 的 3/4 层是线性注意力，cache 无法回退，所以不能用 PLD。** 选型时要注意这一点。

### 质量（人工看 8 条输出）

| 模型 | 零样本 prompt | few-shot prompt |
|---|---|---|
| Qwen3-4B-2507 | 删得太多、改意思（"恶意功能"） | 保守，保留了"问那个""那个就是恶" |
| Qwen3-1.7B | 几乎不改，还会总结丢信息 | 仍然丢信息，翻译只翻了一半 ❌ |
| **Qwen3.5-4B** | 什么都变成列表 | **8 条里 7 条正确**：去口头禅、改口、列表、"UI 搞"→"UI 稿"、翻译 ✅ |
| Qwen3.5-2B | 比较均衡 | 去口头禅不彻底 |

Qwen3.5-4B 在 few-shot 下的输出示例：
- d03 `我们周二开会，不对，是周三开会。大家记得…` → `我们周三开会。大家记得把周报提前发给我。`
- d06 `那个就是恶。我觉得这个功能…` → `我觉得这个功能其实挺好的，但是用户可能不太会用，所以我们是不是应该加一个新手引导？`
- d04 → `今天要做三件事：\n1. 修复登录的 bug\n2. 更新 README 文档\n3. 跟设计师对一下新的 UI 稿`
- 没改对的：d01 留下了"那个，"，d05 的"day to day"（需要个人词典）

## 3. 端到端延迟估算（松开热键之后）

| 阶段 | ~7 s 语音 | ~15 s 语音 |
|---|---|---|
| ASR 最后一段（VAD 切分后 2–3 s） | ~75 ms | ~75 ms |
| LLM 首 token（缓存前缀） | ~75 ms | ~80 ms |
| **首字上屏** | **~150 ms** | **~155 ms** |
| LLM 生成完毕（Qwen3.5-4B，76 tok/s） | +0.3 s | +0.8 s |
| **全部上屏** | **~0.45 s** | **~1.0 s** |

参考：Typeless 约 3.0 s，Wispr Flow 约 1.5 s（第三方实测）。两项都在目标（首字 < 400 ms，全部 < 1.2 s）之内。

## 4. 决定和遗留问题

决定：
- ASR：`mlx-community/Qwen3-ASR-0.6B-8bit`，语言默认 Chinese（自动检测也可以），个人词典同时传给 `hotwords`。
- LLM：`mlx-community/Qwen3.5-4B-MLX-4bit` + few-shot prompt + 前缀缓存 + 流式上屏。暂不需要 PLD。
- 低延迟档 / Phase 3：用 LoRA 微调 Qwen3.5-2B（30 ms TTFT、147 tok/s），目标是达到 4B few-shot 的质量。如果改用纯注意力模型，可以再叠加 PLD。

还没验证的：
- 润色只测了 8 条 **TTS 合成**样本，统计意义很弱。下一步需要**用你自己的麦克风录 30–50 条真实口述**，建一个评测集。
- 还没实现 VAD 分段。分段识别在切点处的精度损失没测过。
- 计时用的是同步解码循环，mlx-lm 自带的异步流水线还能再快一点。
- 个人词典放进 LLM prompt 的效果（d05 "database"）还没测。

## 5. Phase 1 CLI 原型实测（`otl --simulate`，按实时速度输入）

| 场景 | 松开→首字 | 松开→完成 |
|---|---|---|
| 32 s 长句，4 段（段间停顿 0.6 s） | 74–167 ms（5 次里 3 次）；433–607 ms（松开时最后一段还没识别完） | 1.1–1.7 s |
| 6–9 s 单句、中间无停顿（TTS） | 300–450 ms | 0.5–0.85 s |
| 2 s 短句（跳过 LLM） | 132 ms | 132 ms |

- **分段识别没有损失**：8 条样本分段识别和整段识别的平均差异是 0.35%（只有 d02 有 1 处不同）。长句分 4 段的结果和整段识别完全一样。
- **说话时预填充 LLM**：每段识别完立即送进 LLM 预填充。松开后只剩 9 个 token 要预填充，LLM 首字时间从 177–217 ms 降到 52–94 ms，并且不再随语音长度变长。输出和一次性预填充逐 token 一致。
- **单句样本的瓶颈是最后一段的 ASR**：TTS 语音中间没有停顿，整句 6–9 s 只能等松开后再识别，要花 190–330 ms，另外还有约 70 ms 的 LLM 预填充。真人说话停顿更多，最后一段通常更短，需要用真实录音验证。
- GPU 空闲后会稍微变慢：连续调用时 8.7 s 音频识别要 208 ms，空闲 0.5–8 s 后要 230–320 ms，偶尔到 500 ms。在空闲时跑小计算"保温"没有用。
- **润色质量对 prompt 和数值误差都非常敏感**：4 种 prompt 变体在 5 条样本上各错 2 条，只是错的不一样。同一个 prompt，只因预填充的分块方式不同（数值有微小差异），d02 的贪心解码结果就会不同。**用 8 条 TTS 样本调 prompt 没有意义**，需要真实评测集，最终要靠 LoRA 微调。

## 6. 收尾录音（post-roll）

模拟"最后一个字还没说完就松开"（`--release-early-ms`），7 条样本，只看 ASR 原始输出的结尾：

| 场景 | 不收尾（0 ms） | 自适应收尾（≤300 ms） |
|---|---|---|
| 说完才松开 | 全部完整，中位数 299 ms 完成 | 全部完整，**收尾 0 ms**，中位数 277 ms 完成（不增加延迟） |
| 提前 300 ms 松开 | 1/7 丢字（"太慢了"→"太慢"） | 全部完整，中位数 552 ms 完成 |
| 提前 500 ms 松开 | **6/7 丢字**（"会议室"→"会议"、"发给我"→"发给"、"UI 稿"→"UI"…） | **全部完整**，中位数 725 ms 完成 |

只有在你确实还没说完时才多等，等待时间约等于剩下那部分话的长度。

## 7. 润色模型：专用微调小模型 vs 通用模型（AASR-Bench 中文，2026-11-12）

数据：[AASR-Bench](https://huggingface.co/datasets/Andrew0425/AASR-Bench) 的 510 条中文样本，只用文字，没用音频。输入是口语原文（相当于识别完全正确），所以只测润色本身。
打分：把题库里的 3,416 道中文评分题，用字符串匹配自动判分，近似论文里的大模型裁判。有 595 道题无法这样判，没计入。
脚本：`bench/aasr_polish_eval.py`，输出在 `bench/aasr_out_*.jsonl`。

| | 总分 | 内容保留 | 数字/格式 | 去口头禅 | 处理改口 | 延迟中位数 |
|---|---|---|---|---|---|---|
| 不润色 | 59.8 | 94.9 | 21.4 | 74.1 | 2.5 | — |
| AgenticASR-Refiner（MiniCPM-5-1B 微调，MLX 4bit，654 MB） | **79.2** | 88.5 | **59.4** | 96.3 | **69.8** | **0.16 s** |
| Qwen3.5-4B + 我们的 few-shot（现在默认） | 78.1 | 90.5 | 51.7 | 96.3 | 66.0 | 0.53 s |
| Qwen3.5-2B + 我们的 few-shot | 68.7 | 94.0 | 24.9 | 85.2 | 37.8 | 0.27 s |

论文用大模型裁判给 Refiner 打了 80.0 分，和这里的 79.2 接近。

在自己的样本上（8 条 TTS 口述 + 15 条真实使用记录，`bench/compare_polishers.py`）：
- **Qwen3.5-4B**：会修同音错字，会在中英文之间加空格，能听懂"翻译成英文"。但会**把要转述的话当成指令去回复**（"帮我回复一下……"变成了一段回复），会**把英文口述翻译成中文**，也会改用词、删词。
- **Refiner**：很忠实，不会回复你、不会自己翻译，英文保持原样，速度是 4B 的 3–4 倍。但不修同音错字，中英文之间不加空格，偶尔丢掉一两个字（"跟""能够"），"三点"会写成"15:00"，也不会翻译。
- **Refiner 的严重问题**：内容很长、数字很多时（订单号、卡号、地址），它会整段丢内容、写错数字（卡号写错，"五一广场"写成"511广场"），甚至陷入重复循环。这几条 Qwen3.5-4B 全部正确。
